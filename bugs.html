BUG-01

window.ipc.postMessage & window.spid3r.emit drop object payload to ""

Critical spid3r gui / IPC

When JavaScript in a spid3r gui window sends an event with a JSON object as payload, the Rust WebView IPC handler silently coerces/drops payload to an empty string "" instead of serializing it or passing a map. Note that Spid3r's own injected helper window.spid3r.emit(event, payload) does window.ipc.postMessage(JSON.stringify({ event: event, payload: payload })), so passing an object to either API loses all event data.

Minimal Reproducer (spid3r gui repro.matrix)
fn main() -> int {
    gui_on("ui", (ev, payload) => {
        print("ev=" + ev + " type=" + type_of(payload) + " val=" + string(payload));
    });
    gui_eval(r#"setTimeout(function(){
        window.ipc.postMessage(JSON.stringify({
            event: 'ui',
            payload: { sid: 'step1', ok: true }
        }));
    }, 200);"#);
    return 0;
}
Observed Output vs Expected
Actual (logged by handler):
  UI a=ui (string) b= (string)

Expected:
  Either `payload` arrives as a Spid3r `map` or JSON string `{"sid":"step1","ok":true}`, OR `window.spid3r.emit` stringifies non-string payloads instead of silently passing `""`.
Workaround Used
Always JSON.stringify(payload) on the JS side whenever typeof payload !== 'string' before calling window.ipc.postMessage, and run json_parse in Spid3r.
BUG-02

gui_on invokes handler with 2 args blindly, crashing 1-arg handlers at <gui>:0:0

Critical spid3r gui / Events

gui_on(event, cb) accepts a 1-argument closure (such as (ev) => { ... } or (p) => { ... }) without compile-time or registration-time arity validation. At runtime, every incoming IPC event invokes the callback with 2 arguments (event_name, payload), throwing a runtime error inside the event loop so button clicks appear completely dead (and nothing surfaces in WebView2).

Minimal Reproducer
fn main() -> int {
    gui_on("ui", (ev) => {
        gui_title("Clicked");
    });
    gui_eval("setTimeout(function(){ window.ipc.postMessage(JSON.stringify({event:'ui', payload:'hi'})); }, 200);");
    return 0;
}
Observed Stderr Output
error[runtime]: fn expects 1 argument(s), got 2
  --> <gui>:0:0
  stack trace (most recent call first):
    at <script> (<gui>:0:0)

Expected:
  Validate handler arity at `gui_on()` registration time, support both 1-arg `(payload)` and 2-arg `(event, payload)` callbacks cleanly, and report the user's registration source span instead of `<gui>:0:0`.
Workaround Used
Declare the handler with a default second parameter: (a, b = null) => { let ev = if b != null { b } else { a }; ... }.
BUG-03

Calling gui_eval from a spawn fn() background task is silently dropped

Critical spid3r gui / Threading

In native GUI mode, background work must use spawn fn() so CLI probes/builds do not freeze the WebView2 UI thread. While spawn fn() shares module globals with the main thread, any gui_eval(...) (and UI push) executed from inside a spawned worker never evaluates in the live WebView2 window and produces no error.

Minimal Reproducer
fn main() -> int {
    let log_path = env("PROBE_LOG").unwrap();
    gui_on("ready", (_ev, _p) => {
        spawn fn() {
            sleep_ms(400);
            write_file(log_path, "SPAWN_BEFORE_EVAL\n");
            gui_eval(r#"window.ipc.postMessage(JSON.stringify({event:'ui', payload:'"from_spawn"'}));"#);
            append_file(log_path, "SPAWN_AFTER_EVAL\n");
        };
    });
    return 0;
}
Observed Output vs Expected
Actual:
  File log shows `SPAWN_BEFORE_EVAL` and `SPAWN_AFTER_EVAL` both ran,
  no stderr errors printed, yet `gui_on("ui", ...)` NEVER receives `"from_spawn"`.

Expected:
  `gui_eval` / `gui_set_html` / `gui_title` / `gui_emit` should marshal to the `tao` main event-loop thread via an event proxy (e.g. `EventLoopProxy::send_event`) so background workers can trigger UI updates safely.
Workaround Used
Workers only mutate shared state flags (dirty_render = true), while main-thread JS polls on demand only while work is active (window.__studio.setPoll(true, 140)) and shuts polling off when idle.
BUG-04

Live spawn tasks cause 2000ms GUI startup freeze; request_shutdown() fails to close window

High spid3r gui / Lifecycle

spid3r gui runs main() synchronously before opening the tao / WebView2 window. If any spawn fn() task is still alive when main() returns, the runtime blocks window creation for 2000ms waiting to drain tasks. Meanwhile, long loops inside main() prevent the window from appearing at all, and calling request_shutdown() later does not exit the GUI event loop cleanly.

Minimal Reproducer
fn main() -> int {
    gui_title("Drain Delay");
    spawn fn() {
        while not shutdown_requested() {
            sleep_ms(120);
        }
    };
    return 0;
}
Observed Stderr Output
spid3r: warning: 2 task(s) still running after main returned (waited 2000 ms; set SPID3R_TASK_DRAIN_MS to change)

Impact:
  2 full seconds of blank delay before the GUI window initializes, and calling `request_shutdown()` from a flag file does not close the running `tao` window.
Workaround Used
Return 0 from main() with zero spawned tasks running; defer background scans until gui_on("ready", ...) fires (after the window opens), and track/kill PID for hot-reload restarts.
BUG-05

gui_* natives only link in the entry file (unknown name in imported modules)

High spid3r gui / Module Linker

GUI natives (gui_title, gui_set_html, gui_eval, gui_on, gui_emit) are only bound into the top-level entry module scope. Any imported library module that calls them passes spid3r check (or loads without compile-time signature error) and then fails at runtime.

Minimal Reproducer (spid3r gui entry.matrix --dry-run)
// bug_gui_mod.matrix
public fn set_t() { gui_title("hi"); }

// bug_gui_entry.matrix
import "bug_gui_mod" as m;
fn main() -> int { m.set_t(); return 0; }
Observed Verbatim Error
error[runtime]: unknown name 'gui_title'
  --> bug_gui_entry.matrix:2:20
  |
2 | fn main() -> int { m.set_t(); return 0; }
  |                    ^^^^^^^^^
  stack trace (most recent call first):
    at main (bug_gui_entry.matrix:2:20)
Workaround Used
Define 5 one-line wrapper shims inside the entry file (main.matrix) and pass them into framework libraries via app.bridge(studio_title, studio_html, studio_eval, studio_on, studio_emit).
BUG-06

Expression-form if ... elif ... else fails & triggers 24+ duplicate parser error loop

High Compiler / Parser

Spid3r supports if cond { a } else { b } as an expression, as well as statement-form if ... elif ... else, but rejects elif inside an if-expression. Worse, parser error recovery fails to advance past the closing brace and prints error[parser]: unexpected '}' 24+ consecutive times for the same column.

Minimal Reproducer (spid3r check repro.matrix)
fn main() -> int {
    let n = 2;
    let s = if n == 1 { "one" } elif n == 2 { "two" } else { "other" };
    print(s);
    return 0;
}
Observed Verbatim Compiler Output
error[parser]: expected ';' after let, found keyword 'elif'
  --> bug_if_elif.matrix:3:33
error[parser]: unexpected keyword 'else'
  --> bug_if_elif.matrix:3:55
error[parser]: unexpected '}'
  --> bug_if_elif.matrix:3:70
... (exact same error repeated 24 times at 3:70)
Workaround Used
Declare the variable first and assign inside statement-form if ... elif ... else.
BUG-07

Map literal directly inside expression-form if/else branch misparsed as block

Medium Compiler / Parser

Because Spid3r uses { ... } for both code blocks and map literals, returning a map literal from a single-expression if/else branch causes the parser to interpret the inner { ... } as a statement block and fail on the key-value colon.

Minimal Reproducer (spid3r check repro.matrix)
fn main() -> int {
    let x = if true { { "a": 1 } } else { { "a": 2 } };
    print(x);
    return 0;
}
Observed Verbatim Compiler Output
error[parser]: expected ';' after expression, found Colon
  --> bug_if_map.matrix:2:28
  |
2 |     let x = if true { { "a": 1 } } else { { "a": 2 } };
  |                            ^
error[parser]: expected ';' after expression, found Colon
  --> bug_if_map.matrix:2:48
Workaround Used
Assign via statement-form if/else or construct the map via map("a", 1) / helper functions.
BUG-08

Tooling & WASM gaps (fmt BOM/2-pass, ../ imports, 1-file check, WASM state/imports)

Medium CLI / Formatter / WASM
  • UTF-8 BOM inconsistency: spid3r check bom.matrix prints ok and spid3r run bom.matrix succeeds cleanly, yet spid3r fmt --check bom.matrix fails with would reformat.
  • Formatter two-pass convergence: Formatting newly edited .matrix files occasionally leaves a map literal multi-line/single-line difference after pass 1, requiring a second spid3r fmt invocation before spid3r fmt --check passes.
  • Parent-relative imports blocked: import "../rel_target" as r; fails with error[semantic]: invalid module path '../rel_target': imports are relative to the importing file and the module search path (no absolute paths, drive letters, or '..'), forcing manual SPID3R_PATH configuration.
  • Single-file spid3r check CLI: spid3r check accepts only one path per invocation instead of multiple files or directories, adding process-spawn overhead when checking 48+ files.
  • spid3r.wasm limitations: Browser WASM lacks module import resolution, has no gui_* runtime, and resets VM state across sp.eval() calls — forcing AppStudio to bundle modules into one file (`FlatKit.matrix`) and serialize router/state/storage per event.
